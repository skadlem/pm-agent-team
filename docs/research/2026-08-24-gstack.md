# Research: gstack (github.com/garrytan/gstack) and what PMOS can take from it

**Date:** 2026-08-24
**Method:** shallow-cloned the repo (v1.68.x, 41MB), read ARCHITECTURE.md, ETHOS.md, the
`hosts/` adapter system, `docs/ADDING_A_HOST.md`, setup (2,485 lines), skill templates
(SKILL.md.tmpl + resolvers), bin/ CLIs, and the README. Everything below was verified against
the source, not the marketing copy.

## What gstack actually is

Garry Tan's Claude Code skill pack, MIT, 129k stars. 23 slash-command "specialist" skills
(office-hours, plan-ceo-review, plan-eng-review, review, qa, cso, ship, land-and-deploy, ...)
plus ~15 standalone CLIs, all Markdown prompts plus a Bun/TypeScript browser daemon. One
pipeline: Think -> Plan -> Build -> Review -> Test -> Ship -> Reflect, where each skill reads
the previous skill's artifacts.

Key architectural facts (verified in-repo):

1. **Declarative multi-host adapters.** `hosts/*.ts` defines 10 hosts (claude, codex, cursor,
   factory, kiro, opencode, slate, openclaw, **hermes**, gbrain) via a `defineHost()` factory.
   A new host is ONE file of overrides (paths, frontmatter allowlist, tool-name rewrites,
   suppressed resolvers); zero changes to the generator, setup, or tooling
   (docs/ADDING_A_HOST.md). **Hermes is already a first-class host**: `hosts/hermes.ts`
   rewrites "use the Bash tool" -> "use the terminal tool", Write/Edit -> "use the patch
   tool", Read -> "read_file", "use the Agent tool" -> "use delegate_task", CLAUDE.md ->
   AGENTS.md, and suppresses cross-model resolvers Hermes can't run.
2. **Skills are templates, not files.** `SKILL.md.tmpl` + resolver sections are generated per
   host per model (`scripts/gen-skill-docs.ts`), with `--dry-run` drift checks in CI.
3. **Token bill-of-materials.** `bin/gstack-context-bill` audits an installed skills tree:
   what is always-on (frontmatter paid every session) vs per-invocation, `--diff` between two
   trees, `--budget` to enforce a ceiling. Offline by default.
4. **Verification bound to content.** `gstack-wtree` fingerprints the working tree
   (content-stable across rebase/amend); `gstack-evidence run --label <lane> -- <cmd>` wraps
   test commands and records what ran against which fingerprint; `/ship` cites fresh evidence
   instead of re-running suites.
5. **Second opinions and review routing.** `/codex` gets an independent review from a second
   model family; cross-model analysis shows overlapping vs unique findings. Review routing
   picks which reviews apply to a change (CEO doesn't review infra fixes).
6. **Cross-session memory.** `~/.gstack/projects/<repo>/learnings.jsonl` + timeline.jsonl,
   managed via `/learn`; retro writes structured JSON retros from the timeline.
7. **Safety rails.** `/careful` (warns on destructive commands), `/freeze` (restrict edits to
   one directory), `/guard` (both), an egress-receipt hash chain for off-machine sends, and an
   opt-in verify-gate Stop hook that blocks a turn from ending until the project's verify
   command passes.

## Fit with PMOS

gstack and PMOS occupy different layers and COMPOSE:

- PMOS is the **orchestration protocol**: waves, gates, roster, budget, traceability, the
  deterministic harness. gstack has none of this (no budget ledger, no requirement ids, no
  gates — its gates are human-driven slash commands).
- gstack is a **role skill pack** for the execution layer: the exact kind of skills PMOS's
  workers load. PMOS's spawn template embeds "role skills"; those skills can be gstack's.

Constraint: PMOS is zero-pip-dependency stdlib-Python + markdown. gstack's runtime needs
Bun/Node/Chromium. So: borrow PATTERNS freely (MIT), and borrow gstack's skills only where a
PMOS worker's host has them installed — never as a PMOS dependency.

## Concrete integration items (added to docs/plans/2026-08-24-roadmap.md)

Ranked by value/effort:

### G1. Make gstack an optional per-role skill source (SMALL)
roster.json already maps roles to skills. Add an optional block listing gstack commands per
role, conditional on gstack being installed on the worker's host: qa -> `/qa`, `/qa-only`;
backend/frontend -> `/review`, `/investigate`; devops -> `/cso` (OWASP+STRIDE with confidence
gates and verified findings); designer -> `/design-review`; pm -> `/office-hours` (six forcing
questions), `/retro` at checkpoint. The spawn template says "if gstack is installed, use
<command> as your methodology; otherwise follow the built-in procedure". Verified: gstack
installs on Claude Code, Codex, Cursor, Kiro, OpenCode, Hermes — the hosts PMOS would ever
spawn workers on. This is the cheapest way to raise worker quality without changing the
protocol.

### G2. Adopt the defineHost() adapter pattern for L-10 (MEDIUM — reshapes the roadmap item)
PMOS's planned HOST-ADAPTER.md should copy gstack's shape: one declarative config per host
(paths, frontmatter allowlist, tool-name rewrites, suppressed features) + a generator that
renders PMOS's skills/stage files per host. Two concrete wins from reading hosts/hermes.ts:
(a) the Hermes tool rewrites are already battle-tested — PMOS's Hermes backend can copy them
verbatim (Bash->terminal, Write/Edit->patch, Agent->delegate_task, CLAUDE.md->AGENTS.md);
(b) "suppressed resolvers" is the right model for features a host can't do (no swarm usage
reporting -> record with --source estimated; no subagent spawning -> degrade to single-session
waves). Stage S of L-10 (generate Claude Code subagents from roster.json) becomes "generate a
host bundle from roster.json using the defineHost pattern".

### G3. Verification evidence bound to a tree fingerprint (SMALL)
Port the wtree/evidence idea to the QA gate: QA's test-report.md lines gain the working-tree
fingerprint the evidence was produced against (git write-tree of the tested state, or a
content hash of the tested paths). `artifacts.py` can then warn when QA evidence is STALE
(collected against a different tree than the one being gated). This closes a real hole:
today nothing checks that the evidence matches the code being approved. stdlib-only
implementation.

### G4. Context token bill for the template itself (SMALL)
A `tools/context_bill.py` that prices what a session loads: ORCHESTRATOR.md core (always-on)
vs the stage file state.py names (per-stage) vs spawn template vs role skills, in tokens
(len/4, matching kb.py). `--budget` enforces a ceiling so a future protocol edit that bloats
the always-on load fails CI. This measures the P4 split objectively and guards against
regression. gstack-context-bill is the design reference; PMOS's version stays stdlib.

### G5. Cross-model second opinion at high-severity gates (SMALL)
From `/codex`: at GATE 2, when any high-severity open risk exists, optionally re-review the
plan's risk-relevant sections with a second model family (cheap: it reads two artifacts, not
the repo) and show overlapping vs unique findings in the gate summary. Fits PMOS's ladder
infrastructure (the second model is just another ladder entry, paid from the same budget).

### G6. Do-not-touch enforcement as prevention, not detection (MEDIUM)
PMOS catches scope creep at the checkpoint (trace.py unplanned). gstack's `/freeze` prevents
it: a worker declares its `touches:` set at spawn, and where the host supports file-scope
guarding (Claude Code hooks, jcode equivalent), edits outside the set are blocked, not just
reported later. Depends on G2's host abstraction (hook capability is a host feature flag).

### G7. office-hours forcing questions in the charter template (SMALL)
Adopt `/office-hours`' six forcing questions (pain with specific examples, reframe the
framing, challenge premises, alternatives with effort estimates, narrowest wedge) as the
question set the PM worker asks before writing charter.md. Template-only change; raises
charter quality, which everything downstream inherits.

## What NOT to take (skeptical notes)

- **The Bun/Chromium runtime** — violates the zero-dependency promise; PMOS stays stdlib.
  Borrow ideas, never the binary.
- **/design-shotgun, taste memory, iOS QA, browser daemon, GBrain** — interactive solo-founder
  workflows; PMOS's gates already handle the human-in-the-loop part, and none of these map to
  the managed-team model.
- **The ETHOS/LOC marketing** — "810x productivity" is a personal anecdote, not an
  engineering pattern. The parts that matter are the mechanisms (evidence ledger, context
  bill, adapters), which stand on their own.
- **gstack's QA as a substitute for PMOS's wave 4** — gstack QA tests a running app in a
  browser; PMOS QA verifies acceptance criteria against the plan. Use gstack's browser QA as
  one possible EVIDENCE SOURCE inside wave 4 (G1), not as the gate itself.
